A simple solution is easier to understand, verify, and change. This becomes especially clear when you return to your code months later.

## Start with the problem

Before introducing an abstraction, describe the problem in one sentence. An ordinary function is often enough.

Add complexity when there is a concrete reason: repeated behavior, a measured problem, or a new requirement.

## Leave room for change

Small, clear code is easier to replace. Sometimes that is more useful than anticipating every possible scenario.

> A solution should explain the problem it solves.
